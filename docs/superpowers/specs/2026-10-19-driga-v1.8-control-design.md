# Driga v1.8: needs-you inbox, then control, then dispatch

Status: draft for maintainer review, 2026-10-19.
Builds on: v1 design (`docs/specs/2026-10-18-driga-cli-tui-design.md`), v1.5 fleet (`2026-10-18-driga-v1.5-design.md`), Canon contracts (`2026-10-19-canon-contracts.md`).
Evidence: research page https://claude.ai/artifact/Vgn5YwSXsyBqQmfiywzsPv (maintainer data, developer research, 2026 tool landscape, per-agent control surfaces).

## 1. Intent

Driga answers "who is doing what, where, and what needs me?". The maintainer still switches to terminals to find out which session is waiting, and to act on it. On the maintainer's machine, sessions waited on him 224 times in 28 hours (about every 4 minutes during working hours, most waits 5–30 minutes). Developer research ranks "I don't know which session is blocked" as the top complaint across Claude Code, Codex, Cursor and Gemini; approving one action with full context is second.

Claude Remote Control and Codex Remote now offer phone approve and reply for opted-in, logged-in sessions. Driga does not rebuild them. Its job is the part nobody else does: one honest, machine-wide (and later fleet-wide) list of what needs the maintainer and why, with one step to the right place to act. Control is added only where it is officially supported, opt-in, narrow and audited.

The original fleet goal stands: one machine is under pressure (on the maintainer's Mac: memory 86%, swap 98–99%, load 30–40 on 14 cores), so new work should be able to run on a paired machine with headroom. That is step 5 here; steps 1–3 come first because remote work creates more waits.

## 2. The ladder

| Step | What the maintainer gets | Risk | This doc |
|---|---|---|---|
| 1 | Needs-you inbox: why each session waits, for how long, one step to act, desktop alerts. Fleet-wide. | none (read-only) | fully specified |
| 2 | Approve or deny one pending action, with the action shown (Claude, Codex) | medium | outline |
| 3 | Reply to a finished or background session as a new turn | medium | outline |
| 4 | Dispatch a new task on this machine, in its own worktree | high | outline |
| 5 | Dispatch to another paired machine with headroom (A2A) | high | outline |

Each step ships and is used before the next starts. Steps 2–5 get their own design doc before build.

## 3. Goals, non-goals, anti-goals

Goals (step 1):
- Every waiting session on this machine, and on paired fleet machines, appears in the inbox with a reason, a duration and an action.
- The reason is specific when the agent says it: permission prompt, question, idle after a turn, elicitation. When the agent does not say, the item says "waiting" and marks the reason unknown. Never guess.
- One step from an item to the place where the maintainer can act.
- A desktop notification when a session starts waiting, without spamming.

Non-goals (step 1): approving, replying, starting or stopping anything; phone push through a push service; Windows.

Anti-goals (all steps; a build that does these has failed even if it works):
- Auto-approve, or any allow that is not one person's action on one specific request.
- Typing into a live terminal (no tmux `send-keys`, no PTY injection) by default.
- Any traffic off the machine except the existing opt-in fleet links between the maintainer's own paired machines.
- A listener on a public interface.
- Signalling a process driga did not start.
- Merging or committing on the maintainer's behalf.
- Rules or defaults tuned to the maintainer's machine (§2a of the v1 design). The 224-waits figure motivates the work; it does not set thresholds.

## 4. Step 1 in full: the needs-you inbox

### 4.1 Signals

Today: Claude `Notification` hook events become inbox items of kind `waiting`; `Stop` and transcript completions become `finished`; Codex `notify` is ignored (rollouts already give completions); Codex has no waiting signal.

Add:

1. **Claude reason.** Claude's `Notification` hook input carries a `notification_type` (matchers `permission_prompt`, `idle_prompt`, `agent_needs_input`, `elicitation_dialog`) and a `message`. Store the type on the hook event and map it to the inbox reason: `permission` / `question` / `elicitation`. The hook keeps one matcher-less registration (as now), so no settings change is needed for this. Verify the field name against the current hooks reference before building; if absent, reason is `unknown`.
   - `idle_prompt` is **not** a wait. It follows a turn that already produced a `finished` item, so it never creates a `waiting` item or a "needs input" alert. It may only refresh that finished item's age.
2. **Claude background sessions.** Where `claude agents --json` is available, the collector reads it each pass (it is a local CLI call; budget it like other per-pass work, skip when the binary is missing or slow) and uses `state:"blocked"` / `waitingFor` as a second source. Merge rule:
   - The hook sets the reason when both have one; the CLI fills it only when the hook gave none.
   - A session the CLI reports `blocked` with no hook wait creates a `waiting` item (`source: agents_cli`) and alerts like any other. This covers background sessions with no hooks.
   - The CLI saying "not blocked" never ends a hook wait; only the end rules in 4.2 do. `source` is `hook`, `agents_cli` or `both`.
3. **Codex waiting.** A Codex `PermissionRequest` hook registered by `driga hooks install codex`, which **only reports**: it appends a spool event and returns no decision (exit 0, empty output), so Codex behaves exactly as without it. Reason `permission`, with the command when the capture policy allows. This edits `~/.codex/config.toml`, so install shows the diff and asks, like the Claude install. Codex hook timeout semantics must be checked so a slow driga never delays Codex: the hook must return within the existing hook budget (the Claude hook's fast-exit test applies). If the current Codex release has no report-only `PermissionRequest` hook, or it lives outside `config.toml` in a way the byte-preserving install cannot round-trip, step 1 ships without Codex waits and the docs say so; Codex completions keep working as today.
4. **Gemini: deferred from step 1.** Gemini CLI is being replaced by Antigravity CLI for most users and the `agy` schema is still unconfirmed, so step 1 does not add Gemini hooks. A later step adds `Notification`/`ToolPermission` (report-only) once the adapter's attribution is proven on fixtures.

What the item may show is bounded by `capture_text` and, for fleet export, `fleet.share_text`:

| policy | reason | tool name | detail (command or question) |
|---|---|---|---|
| `none` (fleet only) | yes | no | no |
| `titles` | yes | yes | no |
| `snippets` | yes | yes | scrubbed, length-capped |

The reason is a fixed enum, so it is metadata and always shown. Never more than the policy allows, in any surface, alert or export.

### 4.2 Item shape

Extend `model.InboxItem` (schema 2 names, Canon conventions):

- `reason`: `permission` | `question` | `idle` | `elicitation` | `unknown` (only for kind `waiting`).
- `tool`: tool name when known, else omitted.
- `detail`: policy-bounded text (see 4.1), else omitted.
- `waiting_since_at`: when the wait began (UTC); `waited_ms` computed at render.
- `source`: `hook` | `agents_cli` | `both`.
- `jump`: how to get there (4.4), or omitted.

How a wait ends (the existing explicit-signal rule in `CloseAttentionBefore` stays the base):
- **Explicit user signal on that session**, as today: a user prompt, a user tool decision, `tool.blocked_on_user` cleared.
- **The session's own later activity**, for `permission`, `question` and `elicitation` waits only: a tool result, a Stop, or transcript growth from the v1.7 observations on **that same session** after `waiting_since_at`. These waits cannot progress without the person, so the session moving means they answered. Activity of workers or subagents never ends a parent's wait; each item stays on its own session.
- **Ack** by the maintainer.

**Ended is not acked.** A new `ended_at` records an automatic end; `acked_at` stays a person's action, and only acks sync to paired machines as remote acks. Ended waits leave the waiting list but stay in inbox history with their duration. This needs a store column and a schema-2 / fleet field (additive).

**One wait, one item.** An item's ID is the session plus the time the wait began. Further notifications during the same wait (permission, then a question) update its reason and detail; they do not create new items or new alerts.

Order: unacked `waiting` first, oldest wait first; then `finished`, newest first. Same order in TUI, web, `driga inbox list --json` and MCP `list_inbox`.

### 4.3 Surfaces

- **TUI inbox tab (3)**: reason chip, tool, wait duration, machine (fleet), project · branch, title. Enter on an item runs its jump. `x` acks (exists).
- **Web console inbox window**: same rows; the jump shows a copyable command and, where one exists, a link (4.4). Read-only: no POST in step 1.
- **Home and flow views**: the waiting count and oldest wait in the header; flow lead and worker boxes show the reason chip.
- **CLI / MCP**: `driga inbox list --json` and `list_inbox` gain the new fields; schema-2 contract and `docs/contracts/schema2.schema.json` updated with tests.

### 4.4 Jump

Ordered, first that applies; each one is something driga can prove, never a guess:

1. **tmux pane.** If the session's process has a controlling TTY that matches a pane of a running tmux server owned by the user (`tmux list-panes -a -F '#{pane_tty} #{session_name}:#{window_index}.#{pane_index}'`), the jump is that pane. In the TUI, Enter runs `tmux switch-client -t <target>` when driga itself runs inside that tmux server; otherwise it prints the `tmux attach -t <target>` command.
2. **Vendor remote page.** If the session is known to be a Remote Control or Codex Remote session (only when the agent's own records say so), offer that link. Never construct a link driga cannot prove.
3. **Terminal app.** On macOS, if the TTY belongs to Terminal or iTerm2, offer "bring to front" through the app's own scripting interface, opt-in (`[inbox] jump_terminal = true`) because it drives another app.
4. **Fallback.** Show the project directory and the resume command (`claude --resume <id>`, `codex resume <id>`) to copy.

Jump on a fleet item shows the machine name and the command to run there; driga does not open remote shells.

### 4.5 Alerts

- The collector raises a desktop notification when an item becomes `waiting` (macOS: the system notification centre via a documented API or `osascript`; Linux: `notify-send` when present). One per item; a session that waits again later gets a new one.
- **Quiet when present:** no alert if the session showed activity within `alert_after` of the wait starting (the maintainer was already there). `alert_after` default is chosen and validated on held-out recorded sessions per §2a, not on the maintainer's live data; until validated, the default is the conservative choice of alerting immediately.
- **Distinct:** separate titles and sounds for "needs input" and "done"; `finished` alerts are off by default.
- **Throttle:** at most one alert per session per `alert_repeat` window; a summary alert ("3 sessions waiting") when several start within a few seconds.
- **Private:** the alert text follows `capture_text`; with `titles`, it never contains a command.
- Config: `[inbox] alerts = "waiting" | "all" | "off"`, `alert_after`, `alert_repeat`, `jump_terminal`. Each has its `DRIGA_INBOX_*` variable and appears in the generated `.env.example` (strict config rules apply).
- Phone: the web console over the maintainer's own network (Tailscale or SSH tunnel) already shows the inbox live. True push to a locked phone needs a push service off the machine, so it is out of step 1 and needs its own decision.

### 4.6 Fleet

The fleet snapshot already carries inbox rows and remote acks. The new fields travel in the same schema, bounded by `fleet.share_text`. Alerts fire only on the viewing machine and only for machines the viewer has paired; a paired machine never raises alerts on its own for another viewer.

### 4.7 Tests

- Hook fixtures for each Claude `notification_type`, including a missing field, map to the right reason; unknown stays `unknown`.
- `claude agents --json` fixtures (blocked, waiting, missing binary, slow binary over budget) and the agreement rule.
- Codex `PermissionRequest` report-only hook: returns no decision, exits 0 within budget, writes one spool event; install/uninstall diff round-trips and preserves unrelated TOML bytes.
- Item lifecycle: wait ends on newer activity, transcript growth, Stop or ack; ordering identical across TUI, web, CLI JSON and MCP.
- Capture policy: `titles` never shows commands in any surface, alert or fleet export.
- Jump: TTY to pane matching from fixtures; no pane, no jump; never a vendor link without proof.
- Alerts: one per item, quiet-when-present, throttle and summary, distinct kinds, policy-bounded text; notifier is an interface with a fake in tests.
- Tests never touch the real `~/.claude`, `~/.codex`, `~/.gemini` or driga data.

## 5. Steps 2–5 (outline; each gets its own doc)

**Step 2: approve or deny.** A Claude `PermissionRequest` hook of type `http` to driga's loopback endpoint (token-authenticated) and the Codex equivalent. Driga holds the request; the inbox item gains Approve and Deny showing the exact action. If nobody answers before a deadline well inside the hook timeout, driga returns no decision and the agent's own prompt applies. Opt-in per project; never auto-allow; a deny rule in the agent always wins; every decision goes to an append-only audit log. Web actions become POST with token, Origin check and SameSite cookie. Blocking question before design: how a pending hook interacts with Claude's on-screen dialog, and which client gets Codex approvals when several are connected. Test both by hand first.

**Step 3: reply.** A new turn, never typed into a live terminal: `claude -p --resume <id>` (finished), `claude --resume <id> "msg"` (background, where it accepts), `codex exec resume <id>`. Runs under the agent's own permissions. Opt-in.

**Step 4: dispatch here.** Project, agent, prompt, optional new worktree. Driga starts `claude --bg` or `codex exec --json`, records it as driga-started, shows it as a worker in the flow view, and may stop only what it started. Concurrency limit per machine.

**Step 5: dispatch to a paired machine.** A2A v1.0 as the v1.5 design intends. The target's `driga serve` accepts tasks only with `[serve] accept_work = true`, per-project and per-agent allowlists and a concurrency limit. Placement suggests the machine with the most headroom (memory, swap, load, disk from the existing machine samples) that has the repo; the maintainer confirms. The target checks out the branch or makes a worktree, uses its own logged-in agent (credentials never copied), and returns a branch or PR, never a merge. `INPUT_REQUIRED` lands in the same inbox. Running sessions are never moved between machines.

## 6. Decided, and left to the builder

Decided here: the ladder and its order; step 1 read-only; report-only hooks for Codex and Gemini; capture policy bounds every surface; no push service in step 1; no typing into terminals; fleet alerts only on the viewer.

Left to the builder (record each as a judgment call): notifier mechanism per OS; the `claude agents --json` polling budget; exact chip styling in TUI and web; how the summary alert groups; the migration (if any) for new hook-event fields.

Decided after the builder check (maintainer may overrule): `idle_prompt` is not a wait; ended and acked are separate states; worker activity never ends a parent's wait; hook beats CLI for the reason and a CLI-only block still creates an item; Codex waits ship only if a report-only hook exists; Gemini is deferred; reason is always shown, tool name from `titles` up, detail only with `snippets`.

Open, needs the maintainer: whether phone push through a push service is ever acceptable.
