# Driga — v1.5 design: fleet (viewer pulls), verified pairing, Linux collection, MCP, OTLP intake

Status: draft for maintainer review · Date: 2026-10-18 · Builds on the approved v1 design (`docs/specs/2026-10-18-driga-cli-tui-design.md`; its §2a generality rules, §13 privacy rules and anti-goals apply unchanged) and on the transport research (`docs/research/2026-10-18-fleet-transport-evaluation.md`, incl. the 2026-10-18 addendum). Facts marked **[verified]** were checked against primary sources on 2026-10-18 and are cited in the research doc; anything marked **[unverified]** must be checked by the builder before it is relied on.

## 1. Intent

v1 answers "who is doing what, where, and what needs me?" for one machine. The maintainer's agents now also run on other machines: a desktop Mac, a Linux cloud VM or two, occasionally a second laptop. All of them are on a private network of some kind (LAN, cloud VPC, or an overlay such as Tailscale/Headscale/WireGuard). The question stays the same; the answer must now cover the fleet, from whichever machine the maintainer happens to be sitting at, and it must be usable by agents (MCP) as well as humans.

v1.5 adds four things, in this order of importance:

1. **Fleet, viewer-pull.** A machine that opts in runs `driga serve`; a viewer pairs with it once, then pulls an atomic snapshot and follows an event stream. Offline peers stay visible as stale. No hub, no broker, no relay, no always-on central server.
2. **Linux collection.** Cloud VMs are Linux. v1's Linux build returns `ErrUnsupported`; v1.5 implements the platform layer over `/proc` and a systemd user service, so a VM has something to serve.
3. **`driga mcp`.** A stdio MCP server exposing the same read-only views and JSON shapes as the CLI, so a supervising agent on any machine can ask Driga directly.
4. **Optional local OTLP intake.** Claude Code and Codex emit OpenTelemetry natively. When the user opts in, Driga listens on localhost and uses those events to sharpen states (chiefly when a permission wait ended, and whether a session is really working).

The guiding sentence from the maintainer: *"a simple powerful design that works for the majority of use cases."* Where this document chooses between a general mechanism and a simple one that covers private-network fleets of 2–5 machines, it chooses the simple one and says what it does not cover.

## 2. Goals, non-goals, anti-goals

**Goals (v1.5)**
1. From any paired viewer: `driga machines`, merged `driga inbox` / `agents` / `projects` across machines, `--machine <name>` scoping, TUI header and a MACHINE column when peers exist.
2. Inbox latency across machines of a few seconds (target ≤ 5 s hook-to-screen on a LAN; measured, not promised).
3. Pairing that a person can complete in under a minute on two terminals (one of them possibly an SSH session to a headless VM), and that an attacker on the same network cannot silently subvert.
4. Serving costs nothing measurable when no viewer is connected; a connected but idle viewer costs one idle TLS connection per peer.
5. Linux: `driga agents|projects|orphans|machine` correct on a stock Ubuntu/Debian/Fedora VM with Claude Code and Codex installed; held-out Linux fixtures per §2a.
6. `driga mcp` returns byte-for-byte the same envelopes as `--json`.
7. OTLP intake degrades to nothing when not enabled; when enabled, it never creates sessions on its own and never stores prompt or tool content.
8. Binary stays a single cgo-free static build. Today's binary (12.69 MiB stripped) links neither `net/http` nor `crypto/tls`, so the fleet brings the whole HTTP+TLS stack with it: budget **≤ 8 MiB added** (measured standalone: HTTP+TLS+JSON server 6.39 MiB, mTLS pinning +0.5 MiB, MCP stdio +0.9 MiB, JSON-only OTLP intake +0; whole v1.5 network stack 10.36 MiB incl. a protobuf route Driga does not take — research addendum §A.7).

**Non-goals (v1.5)** — later, design must not block them
- Dispatching work to other machines (v2). Intended standard: **A2A v1.0** (task lifecycle `SUBMITTED → WORKING → INPUT_REQUIRED/AUTH_REQUIRED → COMPLETED/FAILED/CANCELED/REJECTED`, JSON-RPC/gRPC/REST bindings, Go SDK `github.com/a2aproject/a2a-go/v2`, client→server HTTP) **[verified]**. Nothing in the fleet wire format assumes or precludes it.
- Web UI / PWA / push notifications (v2).
- Gemini adapter; `claude -p` summaries and `driga ask` (next).
- Windows collection. Linux builds and runs; Windows builds (cross-compile) but has no platform layer. One reason SSH was dropped as the core transport is that Windows' OpenSSH *server* is an optional feature an administrator must add and start (Windows Server 2025 installs it but `sshd` still has to be enabled) **[verified]**.
- LAN auto-discovery (mDNS/Bonjour). Optional later; see §17.
- Cross-machine conflict detection (two machines editing the same path). Different machines can't share a worktree without a network filesystem; out of scope.

**Anti-goals** (inherit v1's; additions)
- Opening a listening port by default, or on all interfaces by default. A port opens only when `[fleet] serve = true` and `listen` names an explicit address.
- A shared CA, a shared secret, or "trust anything on this subnet". Trust is per machine identity, granted by a person, revocable per identity.
- Forwarding or relaying a user's agent telemetry anywhere. The OTLP intake is loopback-only and is installed only when the agent is not already exporting telemetry elsewhere.
- Hiding stale data. A peer that has not been heard from is shown with its last-seen time, never as current.

## 2a. Generality (additions to v1 §2a)

- **No machine-specific network assumptions.** No default addresses, no assumption of Tailscale, no assumption that the viewer is a Mac or the peer is Linux. Every address is configured; every identity is generated.
- **Rules from mechanisms**: staleness from stream state and timestamps, never from hostnames; Linux liveness from `/proc` start times, never from process names.
- **Fixtures from both platforms**: `testdata/fixtures/<adapter>/<version>/heldout/linux-*` from at least one real Linux VM and synthetic Linux process trees (systemd user instance as subreaper, container-style `/proc` without PSI) before v1.5 ships.
- **Pairing works in any terminal** including an SSH session with no clipboard; nothing requires a GUI, a browser, or a QR code.
- **Small-fleet first-class**: one laptop + one VM must be a good experience; a 10-machine fleet must not be a different code path.

## 3. Constraints

Inherited from v1 Global Constraints (`docs/superpowers/plans/2026-10-18-driga-v1.md`): module `github.com/labstack/driga`; no cgo; no fsnotify, no go-git; macOS-specific code only in `*_darwin.go`; `GOOS=linux go build ./...` must succeed; every row carries `machine_id`; JSON envelope `{"schema":1,"observed_at","mode","freshness","coverage_gaps","data"}`; display labels exactly `working · waiting · idle · stalled? · finished · dead · unknown`; text stored per `capture_text`; no destructive action without `y`; reads never acknowledge; no user-specific values in code or defaults; one commit per run; tests never touch the real `~/.claude`, `~/.codex`, or data dirs.

Changed or added in v1.5:

- **Network.** v1's "no network calls anywhere" becomes: *the collector makes no network calls unless fleet is configured.* v1.5 is the first version that can open a listening TCP port — only when `[fleet] serve = true`, bound to the configured address, off by default. The viewer side makes outbound HTTPS connections only to peers the user paired. Git still never fetches. There is still no telemetry from Driga itself and no third-party service.
- **Linux paths.** Data dir on Linux is `$XDG_DATA_HOME/driga` (default `~/.local/share/driga`); config stays `~/.config/driga/config.toml`; spool stays `~/.driga/events/`; collector logs go to the systemd journal when run as a service, else `$XDG_STATE_HOME/driga/collector.log` (default `~/.local/state/driga/`). `DRIGA_DATA_DIR`, `DRIGA_SPOOL_DIR`, `DRIGA_CONFIG` override as before. `config.DataDir()` becomes OS-aware.
- **Footprint.** Collector RSS target stays < 50 MB and < 1 % average CPU with fleet serving enabled and two viewers connected; the footprint script (`scripts/footprint.sh`) gains a fleet phase.
- **Single writer stays.** Remote rows are written into the viewer's DB by the viewer's own collector. The peer's `serve` is a reader plus a spool appender (for remote acks). The CLI never writes the DB; pairing writes trust *files*.
- **Standards on the wire.** TLS 1.3 with mutual certificates, HTTP/1.1 or HTTP/2 as Go negotiates, JSON, Server-Sent Events (`text/event-stream`, `id:`/`event:`/`data:`/`retry:` fields, `Last-Event-ID` on reconnect) **[verified against the WHATWG spec]**. The *schema* inside is Driga's own, versioned. OTLP/HTTP for the local intake per OTLP 1.11.1 (`/v1/logs`, `application/json` or `application/x-protobuf`, 200/partial-success/400/429/503 semantics, gzip) **[verified]**. MCP via the official Go SDK v1.8.0, protocol revision 2026-07-28, stdio transport **[verified]**.

## 4. Decisions

### 4.1 Maintainer's decisions (binding)

- "If there is a standard protocol for our use case, I will go with that" — and, after review, custom is acceptable too ("I am ok for custom as well"): **standard building blocks (TLS, HTTP, JSON, SSE), Driga's own versioned schema on top.**
- **"No hub."** No always-on central server, no broker, no relay. Every machine keeps its own data; viewers pull.
- Machines are **"in network private most likely or cloud VM"**: peers can reach each other over a private network (LAN, VPC, or an overlay). A cloud VM cannot reach a laptop behind home NAT without an overlay; Driga does not add relays (a relay is a hub). The viewer-pull direction means the laptop (viewer) reaches *out* to the VM (peer), which is the common case; a laptop that wants to be *viewed* must be reachable (overlay) or serve nothing.
- **"A simple powerful design that works for the majority of use cases."**
- Approved shape (2026-10-18, after review):
  1. Fleet = **viewer pulls**. Agent machines run `driga serve` (opt-in, off by default, explicit private address). Viewer: `driga fleet add <host[:port]>` ⇒ verified pairing ⇒ mutual TLS. Viewer fetches an atomic versioned snapshot, then subscribes to incremental events over **one** transport: SSE over HTTPS. Peers asleep/unreachable ⇒ stale with last-seen. Laptops normally don't serve. Remote rows stored locally with their `machine_id` by the local collector. A connected remote viewer counts as viewer presence ⇒ fast cadence on the peer.
  2. Wire: HTTPS + mTLS + JSON in Driga's own versioned schema. Rejected for fleet (one line each; details in the research addendum): **OTLP** (push telemetry, no state query), **A2A** (task model is artificial for projects/procs/health; reserved for v2 dispatch), **MCP Streamable HTTP** (credible but more complex; `driga mcp` stays local stdio), **Prometheus/OpenMetrics** (numeric only, cardinality), **ActivityPub / Syncthing BEP / CRDTs** (wrong model: one authority per machine, no merges), **SSH as core transport** (Windows `sshd` off by default; needs sshd on every host), **Raft** (needs a quorum of always-on nodes; Driga has no shared writes), **libp2p / iroh / relays / brokers** (= hub, plus weight). SSH local port-forwarding is *documented* as the way to reach `driga serve` on bastion-only hosts; it is not a second transport.
  3. Pairing security (from Codex review): codes sent over the network can be intercepted ⇒ either a vetted PAKE with certificate binding or a short confirmation code shown on **both** screens, derived from both certificate fingerprints, confirmed by the user on both ends; codes expire, attempts are limited, enrollment closes afterwards; individual viewer identities are authorized (no shared CA trust); unpair/revoke terminates live streams; keys `0600`; renewal/recovery and cloned-VM identity are handled; security groups and host firewalls are the user's job and are documented.
  4. Retention & cursors: the source keeps recent events (reuse v1's 30-day history) plus a per-event monotonic `seq`; atomic snapshot/cursor hand-off; restart epochs; deletions; retention gaps ⇒ re-snapshot.
  5. Access is read-only, **except inbox acks**, a per-viewer permission granted at pairing; a remote ack is appended to the peer's spool (the peer's collector stays the only writer).
  6. **Linux collection is in v1.5**: `/proc`-based platform, PSI where present, systemd user service, Claude/Codex paths verified on Linux, held-out Linux fixtures.
  7. v1.5 scope = fleet pull + verified pairing + Linux collection + `driga mcp` + optional local OTLP intake. Non-goals as in §2.

### 4.2 Claude's calls — check

Each of these is a choice the executor made to fill a gap; none was confirmed by the maintainer. They are collected again in §18's companion list.

1. **`serve` lives inside the collector daemon.** `driga serve` is a foreground `driga collect` with serving forced on; the LaunchAgent/systemd unit runs the collector with `[fleet] serve = true`. One process, one DB handle set, one lock. Fleet therefore requires the daemon on both ends (snapshot mode can neither serve nor pull).
2. **Trust material lives in files, not config.toml and not the DB.** `fleet/identity.key`, `fleet/identity.crt`, `fleet/peers.json` (machines this viewer pulls from), `fleet/viewers.json` (identities allowed to connect), all `0600` in the data dir, written only by `driga fleet …` commands and read by the collector (reloaded on mtime change). `config.toml` holds only `serve`, `listen`, `share_text`, `enroll_window`.
3. **Pairing = numeric comparison with hash commitment, bound to the TLS session**, stdlib only (§7.2). A PAKE is the documented upgrade path, not in v1.5: CPace is still an Internet-Draft (draft-irtf-cfrg-cpace-21, April 2026, not an RFC) with no Go implementation found, and the Go SPAKE2 (RFC 9382) implementations found are unaudited **[verified]**. The commitment makes the 6-digit code as strong as ZRTP's SAS argument: the attacker gets one guess per attempt (RFC 6189 §4.4.1.1) **[verified]**.
4. **Headless peers pre-authorize by identity**: `driga fleet enroll --allow <viewer-id>` on the peer plus `driga fleet add <addr> --id <peer-id>` on the viewer pin both certificate fingerprints up front (Syncthing's device-ID model); no code comparison is needed and no MITM is possible.
5. **Identity = self-signed certificate, verified by pinned fingerprint.** No CA. Go's `tls.Config{InsecureSkipVerify: true, VerifyPeerCertificate: …}` is the documented way to replace chain validation with your own check ("should be used only for testing or in combination with VerifyConnection or VerifyPeerCertificate") **[verified]**; the check is a constant-time comparison of the peer's SHA-256 DER fingerprint against the pinned one. `ClientAuth: tls.RequireAnyClientCert` on the server, same callback.
6. **Device ID format**: SHA-256 of the DER certificate, base32 without padding, with per-group check digits, shown in 8 groups of 7 (Syncthing-style; exact check-digit scheme is the builder's). Short form = first group, used in tables.
7. **Feed table** `feed(seq, epoch, ts, kind, key, payload)` written in the same transaction as each collector pass; one row per changed entity; 30-day retention and a row cap; `resnapshot` when the viewer's cursor is outside what is retained or the epoch differs (§6.3).
8. **SSE conventions**: `id: <epoch>:<seq>`, `event: <kind>`, JSON `data`, `retry: 2000`, a `: ping` comment every 15 s, HTTP 204 to tell a viewer to stop (e.g. revoked).
9. **Presence is forwarded only when the viewer itself has a live local viewer** (TUI or `--watch` heartbeat fresh). A viewer whose collector merely follows a peer does not keep that peer in fast cadence. This narrows the maintainer's "connected remote viewer counts as viewer presence" to "connected *and watched*"; otherwise every served peer would run fast forever.
10. **Views merge all machines by default** when peers exist; `--machine local` restricts to this machine; `--machine <name|id>` to one peer. JSON rows already carry `machine_id`.
11. **Remote inbox items are scoped by `machine_id`**; `driga inbox ack <id>` on a remote item writes a local spool ack tagged with the peer's `machine_id`, which the viewer's collector forwards with `POST /v1/ack`; the item shows `ack pending` until the peer's feed confirms.
12. **What crosses machines**: metadata always (after pairing); titles only with `share_text = "titles"`; snippets only with `share_text = "snippets"` *and* local `capture_text = "snippets"`. **Default `share_text = "titles"`** (§18 item 4). Processes: agent-classified pids only, `cmdline` scrubbed and truncated to 200 chars. Git remote URLs have embedded credentials removed before storage (also locally; v1 gap).
13. **Linux machine health**: `pressure_free` = `MemAvailable / MemTotal × 100` (not the same mechanism as macOS `memory_pressure`, labelled as such); new nullable field `psi_mem_some10` from `/proc/pressure/memory` (`some avg10`) when present. `mem_compressed` = 0 unless zswap/zram counters are readable.
14. **Linux orphan rule**: "reparented to pid 1" becomes "reparented to pid 1 **or** to the user's `systemd --user` instance (a child subreaper)"; validated on Linux held-out fixtures before it ships (§2a).
15. **Linux service** = systemd *user* unit via `kardianos/service` `UserService: true` (POSIX option, verified in the package docs) **[verified]**; `driga service install` on Linux also prints the `loginctl enable-linger $USER` step needed on headless VMs; logs via `journalctl --user -u run.driga.collector`. Non-systemd Linux: `driga service` says unsupported and documents `driga collect` under tmux/nohup.
16. **MCP**: stdio only, read-only tools only (no ack tool), tool per view (§10), no installer in v1.5 (the one-line `claude mcp add` / Codex `[mcp_servers]` snippets are documented; writing agent config stays confined to `driga hooks install`).
17. **OTLP intake accepts OTLP/HTTP JSON only** (`http/json`; stdlib `encoding/json`, zero new dependencies). Protobuf bodies get `415` and a `driga doctor` hint. `driga hooks install --otlp` configures Claude Code with `OTEL_EXPORTER_OTLP_PROTOCOL=http/json` and Codex with `protocol = "json"` (both supported **[verified]**), and refuses when the agent already has telemetry configured.
18. **Default ports**: fleet `7411`, OTLP intake `127.0.0.1:7418` **[not checked against the IANA registry; builder verifies and may change]**.
19. **Migration 0003** changes `repos.path` and `worktrees.path` uniqueness to `(machine_id, path)` and `inbox_items` primary key to `(machine_id, id)`, since remote machines can have identical paths and ids.
20. **Cloned VMs**: `driga machine reset-id` regenerates `machine_id` *and* the fleet identity key/cert and re-stamps local rows; viewers refuse a second device claiming an existing `machine_id` and name the command.

## 5. Architecture

### 5.1 Processes and roles

```
 machine P (peer, e.g. Linux VM)                     machine V (viewer, e.g. laptop)
 ┌──────────────────────────────────────┐            ┌──────────────────────────────────────┐
 │ driga collect  (systemd --user)      │            │ driga collect  (launchd)             │
 │  ├─ sources → derive → SQLite (W)    │            │  ├─ sources → derive → SQLite (W)    │
 │  ├─ feed appender (same tx)          │            │  ├─ fleet puller ──────────────────┐ │
 │  ├─ fleet server  [serve=true]       │◄── mTLS ───┤  │   per peer: hello → snapshot →   │ │
 │  │   GET /v1/hello /v1/snapshot      │   HTTPS    │  │   SSE follow → apply batches (W) │ │
 │  │   GET /v1/events (SSE)            │            │  └─ writes remote rows w/ machine_id│ │
 │  │   POST /v1/ack → spool append     │            │                                      │
 │  │   POST /v1/pair/* (enrollment)    │            │ driga top / driga … (readers, RO)    │
 │  └─ control socket fleet.sock (0600) │            │ driga mcp (reader, RO, stdio)        │
 │ driga fleet enroll (CLI → fleet.sock)│            │ driga fleet add <addr> (CLI pairing) │
 │ OTLP intake 127.0.0.1:7418 [opt-in]  │            │ OTLP intake [opt-in]                 │
 └──────────────────────────────────────┘            └──────────────────────────────────────┘
```

- Every machine runs the same binary and the same collector. "Peer" and "viewer" are roles a machine can have at the same time: a desktop Mac can serve to a laptop and pull from a VM.
- **Peer side** (`[fleet] serve = true`): the collector starts the fleet server as a goroutine group with its own read-only store handle. It never writes the DB; remote acks go through the spool exactly like local hook events (`model.HookEvent{Event:"ack", Adapter:"fleet", Message:<item id>}`), so `drainSpool` needs no new path.
- **Viewer side** (`fleet/peers.json` non-empty): the collector starts one puller goroutine per peer. Pullers decode events into batches; the collector loop applies pending batches in a write transaction at the top of each wake (the loop already wakes at least every second to check the heartbeat), stamping rows with the peer's `machine_id`.
- **Control socket** `fleet.sock` (Unix domain socket in the data dir, `0600`, same-user only): the CLI uses it for `driga fleet enroll` (open window, receive the confirmation code, answer y/N), `driga fleet revoke` (close streams now), `driga fleet status` (live connection state). Nothing on the network can reach it.
- **Readers** (CLI, TUI, MCP) are unchanged in kind: read-only connections, one transaction per view, now across rows from several machines.

### 5.2 Fleet flow

1. **Pair once** (§7): both sides end up with the other's pinned certificate fingerprint, name and `machine_id`; the peer also records the viewer's permissions.
2. **Hello**: `GET /v1/hello` → `{schema, driga_version, machine_id, hostname, os, arch, feed_epoch, feed_seq, share_text, capabilities:["snapshot","events","ack"]}`. The viewer refuses `schema` values it does not know (shows `incompatible`).
3. **Snapshot**: `GET /v1/snapshot` → one envelope (§6.2) built in **one read transaction**, carrying `cursor: {epoch, seq}` = the feed position *inside that same transaction*. SQLite WAL gives readers a consistent view, so every event with `seq > cursor.seq` is strictly after the snapshot and nothing is lost or duplicated.
4. **Follow**: `GET /v1/events` with `Last-Event-ID: <epoch>:<seq>` (the cursor). The server streams every feed row after that position, then live rows as they are committed (the collector signals the server in-process after each write transaction; no polling). Pings keep the connection and the viewer's staleness clock alive.
5. **Apply**: the viewer upserts/deletes rows by natural key (session `adapter+external_id`, repo `path`, worktree `path`, inbox `id`, orphan `id`, proc `pid+start_time`), resolving local integer ids (`repo_id`, `worktree_id`, `session_id`, `parent_session_id`) on insert. Payloads never carry another machine's integer ids.
6. **Stale / reconnect**: on stream loss the viewer marks the peer `stale` (with last-seen), records a coverage gap for that peer from the last event's `ts`, and reconnects with backoff (2 s → 60 s, jittered). If the server answers the resume with a `resnapshot` event, the viewer repeats steps 3–4.
7. **Views**: readers treat remote rows like local ones; freshness per source per machine; a peer's own `sources`/`gaps` rows arrive through the feed, so `driga --machine vm doctor`-style questions ("is the VM's git source fresh?") are answerable locally.

### 5.3 What is published, when

| Feed kind | Emitted when | Payload (natural keys) | Typical rate |
|---|---|---|---|
| `machine` | hello/first pass, then on change | hostname, os, arch, cores, mem_total, driga_version | rare |
| `session` | any stored session field changes (label, evidence, cwd, branch, title, timestamps, parent) | full session row minus text gated by `share_text`; parent by natural key | per pass, only changed rows |
| `session_files` | new file touches (last 30 min window as in v1) | session key + paths + ts | per pass |
| `event` | new `events` rows (hooks, OTLP-derived) | adapter, external_id, ts, kind, summary (gated) | per event |
| `handoff` | new handoff (only if `share_text = "snippets"`) | session key, ts, text | per Stop |
| `inbox` | item created or acked | id, session key, kind, ts, summary (gated), acked_at | per event |
| `repo` / `worktree` | git pass changed a row | path-keyed rows; remote_url credential-scrubbed | per git pass, changed rows |
| `orphan` | candidate appears/changes/disappears | orphan row (ids, evidence, pids, rss) | per procs pass, changed rows |
| `procs` | each procs pass | agent-classified processes only, bulk, cmdline scrubbed/truncated | per procs pass (≤ 1 per 5 s, usually 1 per 60 s) |
| `machine_sample` | each machine pass | sample row | 1 per 10–60 s |
| `source` / `gap` | freshness or gap rows change | row | rare |
| `delete` | retention prune or entity gone | kind + key | hourly batch |
| `resnapshot` | server cannot resume from the viewer's cursor | reason | rare |

- **Inbox latency path**: hook on P → spool append (< 20 ms) → P's collector notices the spool dir mtime on its next wake (≤ 1 s) → `drainOnly` writes the inbox row and the feed row in one tx → server goroutine is signalled and writes the SSE frame (ms) → network → V's puller hands the batch to V's loop (≤ 1 s) → V's TUI polls `data_version` (≤ 1 s). **≈ 2–3 s on a LAN**, within "a few seconds". Measured in the two-process test (§14).
- **Idle cost**: with no viewer connected the peer's only addition is a listening socket and an idle accept loop. With a viewer connected but not watching, one TLS connection with a 15 s ping each way and feed rows at the peer's idle cadence (procs 60 s, git 5 min, machine 60 s) — a few hundred bytes per minute. The viewer's puller is one goroutine per peer blocked on a read. Budget: fleet adds < 5 MB RSS and < 0.1 % CPU on both sides with 3 peers; checked by the footprint script's fleet phase.

### 5.4 Viewer presence

`GET /v1/events?presence=1` is used while the viewer's own `viewer.heartbeat` is fresh (a human is watching `driga top` or `--watch`); when presence changes, the puller reconnects with the other value, resuming from its cursor. While any stream with `presence=1` is connected, the peer's server touches its `viewer.heartbeat` every 4 s, so the existing cadence logic (`cadence(age)` in `internal/collector/daemon.go`) switches to fast mode with no new code path. A one-shot `driga --machine vm agents` does not raise presence.

### 5.5 Remote acks

- Granted per viewer at pairing (`driga fleet enroll --ack`), stored in `viewers.json` as `permissions: ["read","ack"]`.
- `driga inbox ack <id>` where the item's `machine_id` is remote: the CLI appends `HookEvent{Event:"ack", MachineID:<peer>, Message:<id>}` to the local spool (new optional `MachineID` field). The viewer's collector drains it, marks the local copy `ack_pending_at`, and the puller issues `POST /v1/ack {"item_id": …}` to the peer. The peer's server appends the ack to *its* spool; the peer's collector acks the item; the feed's `inbox` update clears the pending flag on the viewer. If the peer is unreachable, the ack stays pending and is retried on reconnect (idempotent). Without permission the CLI fails immediately: `no ack permission on vm (re-pair with --ack)`.
- The TUI's `x`/space on a remote item does the same and shows `ack pending → vm`.

### 5.6 Local OTLP intake

- `[intake] otlp = true` starts an HTTP/1.1 listener on `127.0.0.1:7418` (loopback only; plain HTTP is acceptable on loopback; no auth — any local process can post, and a local process can already edit `~/.claude`, so the intake's authority is deliberately limited: it only *annotates* sessions that already exist from the registry/rollout sources and never creates one).
- Endpoints `/v1/logs` and `/v1/traces` (the latter only to accept Claude Code's beta spans; `/v1/metrics` returns 200 and discards). Accepts `Content-Type: application/json`, optional `Content-Encoding: gzip`; replies per OTLP: 200 with `{}` (full success) or `{"partialSuccess":{"rejectedLogRecords":n,"errorMessage":…}}`, 400 for undecodable bodies (not retried by compliant clients), 415 for protobuf, 429/503 with `Retry-After` under back-pressure **[verified semantics]**. Body limit 8 MiB.
- Decoding uses a minimal stdlib JSON struct: `resourceLogs[].resource.attributes[]`, `scopeLogs[].logRecords[]{timeUnixNano, body, attributes[]{key, value{stringValue|intValue|boolValue|doubleValue}}}` (OTLP/JSON uses lowerCamelCase keys, int64 as strings, enums as integers **[verified]**). Unknown fields are ignored, as the spec requires.
- **At the door**, before anything is stored: attributes `prompt`, `prompt_text`, `response`, `tool_parameters`, `tool_input`, `body`, `body_ref`, `user.email`, `user.id`, `user.account_uuid`, `organization.id`, `vcs.repository.url.full` are dropped. Driga's `hooks install --otlp` never enables `OTEL_LOG_USER_PROMPTS`/`OTEL_LOG_TOOL_DETAILS`; if the user did, the intake still drops the content.
- Mapping to Driga facts: §11. Facts enter `derive.StateInput` as new optional fields (`LastDecision`, `LastAPIRequest`, `LastAPIError`, `LastToolResult`) and the events table (`kind = "otlp:<event.name>"`, summary ≤ 200 chars, scrubbed), capped like other events.
- Degradation: not enabled ⇒ no listener, `driga doctor` shows `otlp intake: off (optional; driga hooks install --otlp)`. Enabled but silent ⇒ `no OTLP events since start` (info, not error). Port busy ⇒ source error `otlp`, everything else continues.

### 5.7 MCP server

`driga mcp` runs an MCP server on stdio (go-sdk v1.8.0; protocol 2026-07-28 negotiated; `StdioTransport.MaxLineLength` set to 4 MiB) **[verified]**. It opens the DB read-only exactly like a CLI read, falls back to snapshot mode with `mode:"snapshot"`, and exposes the tools in §10. Each tool call runs one view builder inside one read transaction and returns the same envelope as `--json` as structured content plus a one-line text summary. Calls never acknowledge anything. Logging goes to stderr only (stdout is the transport). Registration is documented, not automated: `claude mcp add --scope user driga -- driga mcp`; Codex `[mcp_servers.driga] command = "driga" args = ["mcp"]`.

## 6. Wire protocol

All endpoints: HTTPS, TLS 1.3 minimum, mutual certificates, `Content-Type: application/json; charset=utf-8`, request/response bodies ≤ 8 MiB (snapshot responses may be larger: streamed, no limit on the server, 64 MiB cap on the viewer with a `snapshot too large` error). Clock values are RFC 3339 with the *peer's* clock; the viewer records `clock_skew` from the hello round-trip and warns in `driga machines` when |skew| > 60 s.

### 6.1 Endpoints

| Method/path | Auth | Purpose |
|---|---|---|
| `GET /v1/hello` | paired viewer | identity, schema, cursor position, capabilities |
| `GET /v1/snapshot` | paired viewer | atomic full state + cursor |
| `GET /v1/events[?presence=1]` | paired viewer | SSE feed from `Last-Event-ID` |
| `POST /v1/ack` | paired viewer with `ack` | `{"item_id": "…"}` → 202 (spooled) / 403 / 404 |
| `POST /v1/pair/commit`, `/v1/pair/reveal`, `/v1/pair/confirm` | **unpaired**, enrollment window open only | §7.2 |
| anything else | — | 404; unknown client certs get a TLS alert, not an HTTP response, except during enrollment |

### 6.2 Snapshot envelope

```json
{"schema":1,"observed_at":"…","mode":"daemon","freshness":{…},"coverage_gaps":[…],
 "data":{
   "machine":{"machine_id":"…","hostname":"vm-1","os":"linux","arch":"amd64","cores":4,"mem_total":…,"driga_version":"1.5.0"},
   "cursor":{"epoch":"9f3a…","seq":18233},
   "sessions":[…], "session_files":[…], "events":[…], "handoffs":[…],
   "repos":[…], "worktrees":[…], "procs":[…], "orphans":[…],
   "inbox_items":[…], "machine_sample":{…}, "sources":[…], "gaps":[…]
 }}
```

Rows are the existing `model.*` JSON shapes (so `view` builders and MCP need no new types), with these rules: integer ids omitted; parent/repo/worktree references expressed by natural key; text fields blanked per `share_text`; `sessions` = live + ended within 24 h **plus every session referenced by any other row in the snapshot** (parent links, inbox items, events, handoffs, session files), so attribution survives a re-snapshot (Claude's call, from the builder check); `events` limited to 7 d; `inbox_items` 30 d (acked and unacked, so the viewer can show "finished, acked"); `procs` agent-classified only.

### 6.3 Feed, cursors, epochs, retention

- `feed.seq` is `INTEGER PRIMARY KEY AUTOINCREMENT` (monotonic, never reused, survives restarts). `feed_epoch` is a random 128-bit id in `meta`, created on first use and regenerated only when the feed is truncated/reset or the DB is recreated.
- A resume with `Last-Event-ID: epoch:seq` succeeds iff `epoch` matches and `seq ≥ min(seq) retained − 1`; otherwise the server sends one `resnapshot` event and closes. The viewer then takes a fresh snapshot (whose cursor is guaranteed ≥ the current minimum) and resumes.
- Retention: feed rows older than 30 d, or beyond 200 000 rows, are pruned hourly together with v1's prune. A viewer that was away longer than that re-snapshots; that is the "retention gap ⇒ resnapshot" rule.
- Deletions: prune emits `delete` rows for sessions/events/inbox items it removes, so viewers converge; viewers *also* apply their own retention to remote rows by `ts` so a silent peer does not pin rows forever.
- Restart: the collector restarting keeps epoch and seq; its own `gaps` row (v1) is published, so the viewer shows the peer's downtime as a gap rather than inventing one.
- Ordering: feed rows are totally ordered by `seq`; a batch applied on the viewer is one transaction, so readers never see a half-applied pass.

### 6.4 Versioning

`schema` is the envelope's schema number (1 today). Adding fields is compatible; renaming/removing or changing semantics bumps `schema`. The viewer accepts a peer whose `schema` ≤ its own known schema and shows `incompatible (schema N)` otherwise. `driga_version` is informational. The fleet endpoints are versioned by path (`/v1/`); a `/v2/` would coexist during a transition.

## 7. Pairing and trust

### 7.1 Identities

- **Fleet identity** = ECDSA P-256 key + self-signed X.509 certificate (10-year validity, `CN = <machine_id>`, `ExtKeyUsage` server+client), generated on first `driga serve`, `driga fleet id`, or `driga fleet add`. Files `fleet/identity.key`, `fleet/identity.crt` (`0600`, dir `0700`). **Device ID** = encoded SHA-256 fingerprint of the DER certificate (§4.2 item 6).
- **`machine_id`** stays the row key (random 16 bytes in `meta`, v1). The hello binds `device_id ↔ machine_id`; the viewer stores both in `peers.json` and in the `machines` table.
- **Cloned VMs** share both the DB and `fleet/`. `driga machine reset-id` regenerates `machine_id`, the identity key and certificate in one step, re-stamps local rows, and prints that viewers must re-pair. A viewer that sees a *different* device present an already-known `machine_id` refuses it: `vm-1 and <addr> claim the same machine_id; run driga machine reset-id on the clone`. `driga doctor` on a peer warns when the hostname differs from the one recorded at identity creation (cheap clone hint, not proof).

### 7.2 Enrollment with confirmation code (default)

Preconditions: `driga collect` with `serve = true` running on P and reachable at `listen`; V can reach P. Both terminals are watched by the same person (one may be an SSH session).

```
P:  driga fleet enroll [--ack] [--window 10m]
    enrollment open until 14:32 · peer id KQ7NM-…  · listen 10.0.0.5:7411
    on the viewer: driga fleet add 10.0.0.5:7411 --name vm-1
V:  driga fleet add 10.0.0.5:7411 --name vm-1
    connecting… peer id KQ7NM-… (unverified)
P/V (both):  confirmation code  482 913
V:  Does vm-1 show the same code? [y/N] y
P:  Does the viewer (laptop, 7H3QA-…) show the same code? [y/N] y
V:  paired with vm-1 (machine 9f3a…) · read ✓ · ack ✗
P:  authorized viewer laptop (7H3QA-…) · read ✓ · ack ✗ · enrollment closed
```

Step by step:

1. **Window.** `driga fleet enroll` tells the collector (over `fleet.sock`) to open an enrollment window: for `enroll_window` (default 10 min) the TLS server accepts handshakes from *unknown* client certificates, but routes them only to `/v1/pair/*`; at most **3** pairing attempts per window; the window closes on success, on the third failure, or on timeout. Outside a window, an unknown certificate is rejected during the handshake.
2. **Handshake.** V's CLI loads/creates its identity and dials P with TLS 1.3, presenting its certificate; it captures P's certificate from `VerifyPeerCertificate` as a *candidate* (not trusted). Both sides compute `ekm = ConnectionState.ExportKeyingMaterial("EXPORTER-driga-pairing", nil, 32)` (RFC 5705 exporter; Go errors unless TLS 1.3 or extended master secret — TLS 1.3 is required here) **[verified]**. With a man-in-the-middle, V–M and M–P are different TLS sessions with different `ekm` and different certificates on each side.
3. **Commit.** V picks a 32-byte random `nV` and sends `POST /v1/pair/commit {"commit": SHA256(nV)}`. P picks `nP`, stores both commitments, answers `{"commit": SHA256(nP)}`. Nobody has revealed anything.
4. **Reveal.** V sends `POST /v1/pair/reveal {"nonce": nV}`; P checks `SHA256(nV)` equals the commitment (else attempt fails), answers `{"nonce": nP, "machine_id", "hostname", "os", "arch", "driga_version"}`; V checks `SHA256(nP)`.
5. **Code.** Both compute `code = HKDF-SHA256(ikm = nV ‖ nP, salt = "driga-pair-v1", info = fp(cert_V) ‖ fp(cert_P) ‖ ekm)` reduced to 6 decimal digits, shown as `482 913`. Because each party committed to its nonce before seeing the other's, an attacker relaying between two sessions must fix its own nonces blind and has **one chance in 10⁶ per attempt** of producing matching codes on both screens (the ZRTP argument: "the use of hash commitment … constrains the attacker to only one guess to generate the correct SAS" **[verified, RFC 6189 §4.4.1.1]**). With 3 attempts per window the residual is 3 × 10⁻⁶. Binding `fp` and `ekm` ensures the code also differs if the sessions differ in any way the user cannot see.
6. **Confirm on both ends.** V's CLI asks y/N. P's `driga fleet enroll` (via the control socket) asks y/N. V sends `POST /v1/pair/confirm {"name": "laptop"}` only after its `y`; P's server completes the request only after P's `y` (2-minute timeout). Either `N` fails the attempt; both sides discard the candidate.
7. **Persist.** P appends `{device_id, name, machine_id?, permissions:["read"(,"ack")], paired_at, enrolled_from: <addr>}` to `viewers.json`. V appends `{name, addr, device_id, machine_id, hostname, os, paired_at}` to `peers.json`. Both files are written atomically (temp file + rename), `0600`.
8. **Use.** From now on every connection from V presents the same certificate; P's `VerifyPeerCertificate` accepts only fingerprints in `viewers.json`; V's accepts only the fingerprint in `peers.json` for that address. No code, no password, nothing to type again.

### 7.3 Headless peers: pre-authorization by identity

When nobody can answer y/N on P (a VM reached only through an SSH session that will be closed, or automation), the IDs replace the code:

```
V:  driga fleet id            → 7H3QA-…  (this machine's device id)
P:  driga fleet enroll --allow 7H3QA-… [--ack]   → prints peer id KQ7NM-…, returns immediately
V:  driga fleet add 10.0.0.5:7411 --name vm-1 --id KQ7NM-…
```

P accepts a pairing only from a client whose fingerprint equals the allowed ID; V refuses unless P's fingerprint equals `--id`. Both identities are verified before anything else; the commit/reveal exchange still runs (same code path) but no prompt is shown. This is Syncthing's device-ID model and is immune to man-in-the-middle by construction. It costs copying two 56-character IDs — through the SSH session the user already has.

### 7.4 Permissions

`read` (always) and `ack` (opt-in: `--ack` at enrollment). Changing a viewer's permissions later = `driga fleet revoke <id>` and re-enroll (no in-place edit command in v1.5; keeps the trust file write paths to two).

### 7.5 Revocation, unpair, renewal, recovery

- **Peer side**: `driga fleet revoke <viewer-id|name>` removes the entry from `viewers.json`, tells the server over `fleet.sock` to close that viewer's streams **now** (SSE ends with HTTP 204 semantics for the next reconnect, so a compliant client stops), and prints what was removed. `driga fleet viewers` lists authorized viewers with last-connected time.
- **Viewer side**: `driga fleet remove <name>` (alias `unpair`) removes the peer from `peers.json`, stops its puller, keeps the peer's rows (they age out by retention) unless `--purge`. `driga fleet peers` lists peers with state.
- **Both**: an unexpected fingerprint for a known address is never auto-accepted: the viewer logs `peer identity changed` and marks the peer `untrusted`; the user runs `remove` and pairs again.
- **Renewal**: certificates are valid 10 years; there is no rotation without re-pairing (`driga fleet rekey` regenerates the identity and prints that all pairings are void). Simplicity over PKI.
- **Recovery**: a lost data dir means a new identity (and a new `machine_id`); viewers see the old peer as stale forever until removed and the new one is paired. A lost `peers.json` on the viewer means re-pairing; the peer's `viewers.json` entry for the viewer's old identity is harmless but should be revoked.

### 7.6 Storage

`fleet/` in the data dir: `identity.key`, `identity.crt`, `peers.json`, `viewers.json`, `fleet.sock` (socket), `enroll.json` (transient window state), all `0600`, dir `0700`. `driga doctor` checks modes and refuses to serve if the key is group/world readable (same rule as OpenSSH's).

### 7.7 What an attacker on the same network can and cannot do

| Attacker | Can | Cannot |
|---|---|---|
| Passive on the LAN/VPC | see that a TLS 1.3 service runs on `listen`; see connection timing and sizes | read any payload; learn certificate identities (TLS 1.3 encrypts certificates); learn session titles, paths, inbox contents |
| Active, no enrollment open | connect and be rejected at the handshake; burn CPU (bounded: accept rate-limited to 10/s, ≤ 16 concurrent connections, handshake timeout 5 s); port-scan | obtain data; ack anything; make the peer trust it |
| Active during enrollment (≤ 10 min, ≤ 3 attempts) | attempt a man-in-the-middle; succeed with probability ≤ 3 × 10⁻⁶ if the user compares codes; succeed with probability 0 with `--allow`/`--id` | guess offline (nothing to guess offline); keep trying after the window closes |
| Holds a stolen `identity.key` of a viewer | read what that viewer was allowed to read; ack if that viewer could | affect other viewers; write anything else |
| Holds a stolen `identity.key` of a peer | impersonate that peer to viewers that trust it (feed them false state) | read viewers' data; reach other peers |
| Local user on the same machine (other uid) | nothing (files `0600`, socket `0600`) | — |

Host firewalls and cloud security groups are the user's responsibility: Driga documents that `listen` should be an address on the private network and that the port should be allowed only from the viewer's addresses. Driga refuses `listen` on `0.0.0.0`/`::` and on addresses that are not loopback, RFC 1918, link-local, ULA, CGNAT (100.64/10, which Tailscale uses) or an interface name, unless `allow_any_address = true` is set (§18 Q1).

### 7.8 Why not a PAKE in v1.5

A PAKE (the pairing code as a password that derives the key) would remove the "compare on both screens" step. The maintainer asked for a *vetted* one. On 2026-10-18: CPace is still an Internet-Draft (draft-irtf-cfrg-cpace-21, "In IESG Review"), not an RFC, with no Go implementation found; SPAKE2 is RFC 9382 (Informational, CFRG, Sept 2023), and the Go implementations found (`CzarJoti/gospake2` v0.1.6, Feb 2026, MIT, module-path confusion with `ValiantChip/gospake2`; `salsa.debian.org/vasudev/gospake2`, 2021, "has not been formally audited"; `jtejido/spake2`, "NOT FOR PROD") are none of them audited **[verified]**. The confirmation-code protocol above uses only `crypto/*` from the standard library and a published argument (ZRTP). When an audited, cgo-free Go PAKE exists, it slots into the same `/v1/pair/*` exchange (the code becomes the password; the `ekm` binding stays) without changing identities, files or CLI.

## 11. OTLP intake mapping

Correlation key: resource `service.name` ∈ {`claude-code`, `claude-code-desktop`} ⇒ adapter `claude`; attribute `session.id` ⇒ Claude `external_id` (the registry's `sessionId`; **equality to be confirmed on a fixture**). What the intake does **not** do: it never creates a session (a `session.id` with no registry/rollout match is counted in `driga doctor` as "unmatched OTLP sessions: n" and otherwise ignored), never changes `liveness` (that stays pid/registry evidence), and never replaces the hooks — `Notification(permission_prompt)` / `PermissionRequest` hooks remain the source for the *start* of a wait.

## 12. Privacy — what crosses machines by default

| Data | Leaves a peer by default (after pairing)? | Gate / note |
|---|---|---|
| hostname, os, arch, cores, total memory, Driga version | yes | hello |
| session: adapter, origin, kind, pid, cwd path, branch, label, heuristic flag, evidence, timestamps, parent link | yes | metadata |
| titles (`ai-title`, `display_title`), git commit subjects | **yes** (default `share_text = "titles"`) | set `share_text = "none"` to withhold |
| last prompt, handoff text, inbox summaries with text | **no** | `share_text = "snippets"` and local `capture_text = "snippets"`; ≤ 200 chars, scrubbed |
| inbox items (kind, ts, acked) | yes, with generic summaries (`turn finished`, `waiting for input`) unless gated above | — |
| file paths touched | yes | metadata (same class as cwd) |
| repo path, name, branch, ahead/behind, dirty counts, last commit subject | yes | remote URL with credentials stripped; commit subject is text but is a git fact, not agent text (builder: gate behind `titles`? see §18 Q4) |
| processes | agent-classified only; `cmdline` scrubbed, truncated to 200 chars; `exe`, role, rss, cpu | — |
| machine samples | yes | — |
| orphan candidates (ids, signature, evidence, pids, rss) | yes | — |
| source freshness, coverage gaps | yes | — |
| user names, emails, API keys, transcripts, prompts beyond the gated snippet | never collected | — |
| OTLP intake content (`prompt`, `response`, tool input/params, bodies, `user.*`, `organization.id`) | never stored locally, so never shared | dropped at the door |

Local storage of remote data follows the same rules as local data (`0600`, retention). A viewer with `capture_text = "titles"` that pairs with a peer sharing snippets stores those snippets (the peer chose to share them); the viewer's `driga fleet peers` shows each peer's `share_text`.

## 13. Failure modes

| Situation | Behaviour |
|---|---|
| Peer asleep / unreachable / firewalled | stream drops ⇒ `stale (last seen 12m)`, rows dimmed, reconnect with backoff; coverage gap recorded for that peer |
| Peer collector stopped (`driga service stop`) | port closes ⇒ same as above; `driga machines` shows `stale`, not `off` (indistinguishable from the viewer's side) |
| Viewer collector not running | `driga machines` shows peers with last-applied data and `viewer collector not running`; snapshot mode shows local only |
| Peer identity changed (fingerprint mismatch) | `untrusted`, never auto-accepted; message names `driga fleet remove` + re-pair |
| Same `machine_id` from two devices (clone) | second refused with the `reset-id` message |
| Schema newer than the viewer understands | `incompatible (schema 2)`; no rows applied |
| Epoch changed / cursor older than retention | `resnapshot` ⇒ fresh snapshot ⇒ resume; counted in `driga fleet status` |
| Slow viewer (server buffer of 1 000 events full) | server closes the stream with a final `resnapshot`; viewer re-snapshots |
| Clock skew > 60 s | warning in `driga machines`; ages still computed from the peer's timestamps |
| `listen` not private, or port in use, or identity key readable by others | serve refuses to start with a clear message; collector continues without serving; `driga doctor` shows the reason |
| Enrollment attempts exhausted / window expired | `enrollment closed (3 attempts)`; `driga fleet enroll` again |
| Remote ack with no permission | immediate error; nothing spooled |
| Remote ack while peer unreachable | `ack pending`, retried on reconnect, idempotent |
| Snapshot larger than 64 MiB | viewer refuses, shows `snapshot too large`; peer's `driga doctor` suggests retention/`--purge` |
| Linux without PSI / in a container without `/proc/pressure` | `psi_mem_some10` null; machine view shows `psi n/a` |
| Linux without systemd | `driga service install` unsupported with instructions for `driga collect` under tmux/nohup |
| Linux agent registry file absent (unverified path) | Claude adapter tolerant mode; `driga doctor` names the missing source |
| OTLP intake port busy | source error `otlp`; everything else continues |
| OTLP bodies with content attributes | dropped at the door; counted in doctor ("content attributes dropped: n") |
| Bastion-only host | documented: `listen = "127.0.0.1:7411"` on the host, `ssh -N -L 7411:127.0.0.1:7411 host` on the viewer, `driga fleet add 127.0.0.1:7411 --name host`; the pinned certificate makes the tunnel's endpoint identity irrelevant |

## 14. Testing and validation

- **Pairing**: table tests for the commit/reveal state machine (wrong commitment, replayed nonce, missing confirm, timeout, attempt cap, window expiry); a deterministic test vector for the code derivation; a man-in-the-middle test that relays two in-memory TLS sessions and asserts the two codes differ; `--allow`/`--id` pinning tests (wrong id refused).
- **Trust**: unknown client cert rejected at handshake outside a window; revoked viewer's open stream closed within 1 s; fingerprint mismatch marks `untrusted` and applies nothing.
- **Feed and cursors**: snapshot cursor equals the last feed `seq` visible in the snapshot's transaction; resume from `seq` yields exactly the rows after it; epoch change and pruned cursor produce `resnapshot`; deletions propagate; a batch is applied atomically.
- **Two-process fleet test (no real network)**: `driga collect` with `DRIGA_DATA_DIR=$tmpA`, `[fleet] serve = true, listen = "127.0.0.1:0"` (port 0 allowed in tests; the chosen port is written to `fleet/listen` for the test to read) and a second `driga collect` with `$tmpB` pairing via `--allow`/`--id`; fixtures drive A's sources (file-backed fake platform as in `internal/validate`); assert B's DB contains A's rows with A's `machine_id`, that a hook appended to A's spool appears in B's inbox within 5 s, that presence toggles A's cadence, that an ack from B lands in A's spool and comes back acked, that stopping A makes B show `stale`, and that restarting A resumes from the cursor without re-snapshot. Both processes use temporary HOME directories; nothing touches real agent dirs.
- **Linux platform**: `/proc` parsers tested against a synthetic `/proc` tree in a temp dir (`procRoot` override): stat/status/cwd/fd/net tables, PSI present and absent, systemd-user subreaper; held-out fixtures `heldout/linux-vm-*` (synthetic now; at least one scrubbed real VM sample before release, provenance without personal data) with human-written `expected.json`, never copied from output; CI job runs `go test ./...` on `ubuntu-latest` in addition to macOS.
- **MCP**: in-memory transport tests calling every tool and comparing the structured content byte-for-byte with the CLI's `--json` output on the same temp DB; a test that no tool changes `acked_at`.
- **OTLP intake**: golden tests with scrubbed captured Claude Code payloads (JSON, gzip, partial, oversize, protobuf ⇒ 415), fuzz test on the decoder, and a derive test that a `tool_decision(user_temporary)` clears `waiting` while `tool_decision(config)` does not. A Codex capture fixture is a prerequisite for any Codex mapping.
- **§2a held-out validation** extends to fleet: synthetic feed traces (out-of-order application attempts, duplicate seq, missing epoch) and state labels for remote sessions must match `expected.json`; thresholds (staleness 45 s, backoff, window, attempts) are documented defaults, not tuned to one network.
- **Footprint**: `scripts/footprint.sh` gains a fleet phase (serve with 2 connected viewers, 10 min) and must stay under the v1 budget; the stripped binary size is recorded in the release checklist.

## 18. Resolved questions (2026-10-18)

The maintainer approved the direction ("Go implement test") and left these to the executor; each is Claude's call — the maintainer may overrule any.

1. **Non-private listen addresses:** refused unless `allow_any_address = true`. Public-IP VMs are reached via overlay or SSH port-forward (documented).
2. **Merged views by default:** yes. With peers paired, every view, the TUI, JSON and MCP show all machines; `--machine local` narrows.
3. **Pairing method:** the stdlib confirmation-code protocol (commit/reveal bound to the TLS exporter, code on both screens, `--allow`/`--id` for headless). No unaudited PAKE dependency.
4. **`share_text` default: `titles`** (supersedes §4 item 12's `none`), matching the local `capture_text = "titles"` default; the peers are the user's own paired machines. Snippets still need `share_text = "snippets"` on the peer and `capture_text = "snippets"` locally. Git commit subjects count as titles (gated by the same setting).
5. **Linux service:** systemd user unit + documented `loginctl enable-linger`; other init systems run `driga serve` in the foreground (documented, not supported by `driga service`).
6. **OTLP intake:** JSON only; when the agent already exports telemetry elsewhere, `hooks install --otlp` refuses and explains.
