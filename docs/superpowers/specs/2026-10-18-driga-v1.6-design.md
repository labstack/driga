# Driga — v1.6 design: Gemini/agy adapters, cleanup, `claude -p` summaries, `driga ask`

Status: approved by delegation (maintainer: "You judge", 2026-10-18) · Date: 2026-10-18 · Builds on v1 (`docs/specs/2026-10-18-driga-cli-tui-design.md`) and v1.5 (`docs/superpowers/specs/2026-10-18-driga-v1.5-design.md`). Their generality rules (§2a), privacy rules (v1 §13) and anti-goals apply unchanged. **[verified]** = checked against a primary source on 2026-10-18; **[unverified]** = the builder checks before relying on it.

## 1. Intent

The v1 and v1.5 roadmaps defer three items to "next": a Gemini adapter, LLM project summaries through the user's own `claude -p`, and `driga ask`. The maintainer added a fourth: Driga already reclaims memory and CPU (orphan kill), but agents also leave disk behind — worktrees, build output, temp dirs, history — and cleanup of those should be designed as carefully as orphan kill. Gemini is a third agent family people run next to Claude Code and Codex; since 2026-06-18 Google no longer serves Gemini CLI to individual accounts and points them to the Antigravity CLI, `agy`, a closed-source Go binary **[verified: secondary sources; Google's migration guide is antigravity.google/docs/gcli-migration, unverified]**. Enterprise and API-key users keep Gemini CLI, so both exist in the field. Summaries replace the composed project line (v1 §7: handoff → title → commit subject) with one sentence that reads well. `driga ask` lets a person ask the fleet a question in plain words; it reuses `driga mcp` instead of inventing a query language.

## 2. Goals, non-goals, anti-goals

**Goals**
1. Gemini CLI and `agy` sessions appear in `agents`, `projects`, the inbox, conflicts and the TUI, with the same states as other adapters, on macOS and Linux.
2. `driga cleanup` lists disk that agents left behind, with evidence and reclaimable size, and removes a candidate only after re-verification and `y` (§4.4).
3. Project summaries are opt-in, cached, cheap, and never block a view: a view shows the cached summary or the v1 composed line.
4. `driga ask "<question>"` answers from Driga's read-only data through `claude -p`, with the `driga mcp` tools as its only tools.

**Non-goals**
- Summaries or `ask` through any model other than the user's installed `claude` CLI. There is no API key and no direct Anthropic API call (v1 §3).
- A Gemini OTLP intake; it can come later if Gemini emits OTLP logs that fit v1.5 §5.6.
- Dispatching work (v2, A2A).

**Anti-goals**
- Sending transcript content to a model. Summary inputs are limited to data Driga already stores under the effective `capture_text` (§4.2).
- A summary that looks fresher than its inputs. Every summary shows its age and its source.
- Driga's own `claude -p` runs showing up as agent sessions, or firing Driga's hooks.
- Deleting anything automatically, deleting an agent's own history, or deleting anything that cannot be restored from git or the OS trash without the person seeing that exact list first (§4.4).

## 3. Constraints

All v1.5 Global Constraints still apply: no cgo; single writer; JSON envelope; tests never touch real `~/.claude`, `~/.codex` or `~/.gemini`; held-out fixtures; no curve-fitting.

## 4. Design

### 4.1 Gemini CLI adapter (`gemini`)

**Storage [verified against `packages/core/src/services/chatRecordingService.ts` on `main`]:**
- **Location:** sessions live in `<project temp dir>/chats/`.
- **Main session names:** `session-<ISO timestamp, 16 chars, ':'→'-'>-<first 8 of session id>.jsonl`.
- **Subagent sessions:** `chats/<parentSessionId>/<sessionId>.jsonl`.
- **Format:** JSONL, append-only. One exception is recovery, which rewrites through a temp file and a rename.
- **Record kinds, classified in this order:**
  - metadata header (`sessionId`, `projectHash`, `startTime`, `lastUpdated`, `kind` = `main`|`subagent`, `directories`, `summary`);
  - message (`id`, `timestamp`, `type` = `user`|`gemini`|…, `content`, `toolCalls[{id,name,result,…}]`, `tokens`, `model`);
  - `{"$set":{…}}`;
  - `{"$rewindTo":"<id>"}`;
  - `{"$patch":{…}}`.
- **Legacy files:** older versions wrote whole-file `session-*.json` (one object with `messages`). A legacy file is migrated to `.jsonl` on load. Both forms exist on real machines.

**Root:** `~/.gemini/tmp/<dir>/`. The project directory name is a hash or a short project name; each directory holds a `.project_root` file with the project's absolute path. The builder confirms `.project_root` and any `GEMINI_CLI_HOME`-style override against the Gemini source **[unverified]**.

**Reading:**
- `.jsonl` uses the existing `tail` offsets.
- A rewrite by rename, or a file shorter than its stored offset, resets the offset to 0, as the other adapters already do.
- A legacy `.json` file is re-read whole only when its size or mtime changes. Files over 8 MiB are skipped with a `skipped_backlog` warning.

**Folding:**
- `$rewindTo` removes later messages from the fold.
- `$set.summary` is the session title.
- A `user` message sets `LastPromptAt`.
- A `gemini` message after the last `user` message ends the turn.
- A `toolCalls` entry without a `result` keeps the turn open.

**Files touched:** tool calls named `write_file`, `replace` and `edit` (from the Gemini tool registry) with a path argument. The builder confirms the argument names **[unverified]**.

**Sessions:**
- Subagent files link to their parent session. This is new: today's family linking (`internal/derive/family.go`) uses process ancestry only, so `model.SessionObs` gains a `ParentExternalID` (same adapter), and the collector resolves it to `parent_session_id`. `agy` can use it if its schema has a parent link.
- Process detection: a `node` or `gemini` process whose argv contains the Gemini CLI entry point. This uses the same signature mechanism as Claude and Codex.

**Hooks:** Gemini CLI has a hooks system **[unverified: names, payloads, config path]**. If it supports a notification or permission-wait hook, `driga hooks install` gains `--agent gemini`. Otherwise Gemini never shows `waiting`: an unfinished tool call may still be executing, and v1 §7.1 rejects that inference. Like Codex without hooks today (`internal/derive/state.go`), an open turn with recent activity is `working`, and a silent one is `unknown`.

**Fixtures:** held-out real fixtures come from at least two Gemini versions, including one legacy `.json` file and one with `$rewindTo`. They are made by the maintainer or volunteers with content redacted; synthetic files cover `$patch` and subagents.

### 4.1a Antigravity CLI adapter (`agy`) — staged

`agy` 1.4.2 is installed on the maintainer's Mac. Its state lives under `~/.gemini/antigravity-cli/`, with one SQLite database per conversation in `conversations/<id>.db`, plus `brain/`, `implicit/`, `annotations/` and `log/` **[verified: directory and file-type listing only]**. The format is closed and undocumented, so:

- **Schema discovery** is a maintainer-run step: `driga dev agy-schema` prints table and column names and row counts, never values, from the user's own databases. That output plus redacted synthetic databases become the fixtures. No adapter code is written against guessed tables.
- **Opened read-only** (`mode=ro`, `immutable` off, short busy timeout); a locked or unreadable DB is a `source` warning, never a retry loop.
- **Version-gated.** `TestedVersions()` lists the `agy` versions whose schema matched; an unknown version still shows process-level sessions (pid, cwd, liveness from the process table) and marks title/state coverage as `unsupported-version` instead of guessing.
- **Process detection** by the `agy` executable; the cwd comes from the process, as for other agents.
- The adapter never writes to `agy`'s files and never reads `brain/` or `knowledge/` content.

If the schema turns out to lack a usable timestamp or session-to-project link, v1.6 ships `agy` as process-level only, and says so in `driga doctor`.

**Staging (ruling, 2026-10-18):** the maintainer's permission policy blocks Claude from opening the real `agy` databases, even a copy, so no real schema is available yet. v1.6 therefore ships:
- `agy` process-level sessions;
- `driga dev agy-schema`, which the maintainer runs themselves;
- a `doctor` line `agy: process-level (schema not yet supported)`.

The transcript-level `agy` adapter is a follow-up built from that command's output.

### 4.2 Summaries through `claude -p`

**Off by default.** Enabled by `[summaries] enabled = true`. Running `driga summarize` while summaries are off explains how to enable them and exits.

**Inputs:** the effective `capture_text` bounds them. `summarize` gathers them at run time, read-only: stored rows, plus one `git log -5 --format=%s` per worktree, because the collector keeps only the latest subject:
- project name, branch, dirty/ahead/behind counts;
- the last 5 commit subjects;
- session titles from the last 24 h;
- handoff text, only when `capture_text = "snippets"`.

No transcript lines, no file contents, no paths beyond the project name.

**When:** on demand. `driga summarize [project…]` and a TUI key (`S`) run it. No background LLM calls, because a background call spends the user's quota without asking (my call; see §6, question 2).

**How [verified against `claude --help`, Claude Code 2.1.303]:**
- Driga runs:

  ```
  claude -p --safe-mode --no-session-persistence --tools "" --output-format json --json-schema <schema> --model <cheap model> --max-budget-usd 0.05 --name driga-internal
  ```

  - `--safe-mode` disables hooks, MCP servers, CLAUDE.md, skills and plugins, but keeps auth.
  - `--no-session-persistence` writes no transcript, so no adapter sees the run.
  - `--name driga-internal` lets process classification ignore the run.

  `--bare` is not used: it accepts only `ANTHROPIC_API_KEY` auth, so it fails for subscription users.
- Before each run, Driga reads `claude --help` once and checks that every flag it needs is present. When one is missing, it fails closed with `claude <version> lacks --<flag>`.
- The prompt asks for one sentence of at most 120 characters.
- The child also gets `DRIGA_INTERNAL=1`, so `driga hook` drops any event from it, as a second guard against recursion.

**Cache:**
- The summary is stored in a new `summaries` table: `project_id`, `input_hash`, `text`, `model`, `created_at`.
- A summary whose input hash no longer matches is shown as `(stale)` until refreshed.
- The CLI never writes the DB, so `summarize` writes its result through the spool and the collector ingests it. This is the same path acks use.

**Fleet:** summaries replicate as a new feed kind, `summary`. Each summary records `used_snippets` (true when handoff text was an input). The feed shares a summary only when the peer's `share_text` ≥ `titles`, and a `used_snippets` summary only at `snippets`. This keeps v1.5's snippet gate (`internal/feed/feed.go`) intact. At `titles`, a peer with snippet capture on also keeps a titles-only summary to share; it costs at most one extra `claude -p` call per refresh.

**Display:** `projects` shows the summary with `· claude 3h` source and age, or the v1 composed line when there is none.

### 4.3 `driga ask`

- `driga ask "<question>"` runs:

  ```
  claude -p --setting-sources "" --strict-mcp-config --mcp-config <temp file registering only `driga mcp`> --tools "" --allowedTools "mcp__driga__*" --no-session-persistence --name driga-internal --output-format stream-json
  ```

  - `--setting-sources ""` loads no user, project or local settings, and with them no hooks or plugins.
  - The run also gets `DRIGA_INTERNAL=1`.
  - `--safe-mode` is not used here because it disables MCP servers.
  - The same flag probe as in §4.2 applies **[verified flags exist]**. Whether `--mcp-config` servers load under `--setting-sources ""` is checked by the builder **[unverified]**. Driga fails closed with a clear error if they don't.
- The answer streams to stdout. `--json` returns the `claude -p` result object inside Driga's envelope.
- `ask` needs no summaries opt-in: the person typing the question is the consent. It is still never run in the background.

### 4.4 Cleanup: disk that agents leave behind

**Principles** (carried over from orphan kill, v1 §8):
- Driga proposes; the person disposes. Nothing is removed automatically or in the background.
- Every candidate carries its evidence and its reclaimable size.
- Every action is **re-verified at the moment it runs**, the same way `kill.VerifyIdle` re-checks an orphan. If any condition no longer holds, the action is refused with the reason.
- Every action needs `y`, or `--yes` in scripts. `--dry-run` prints exactly what would run.
- Every action appends a line to `<data dir>/cleanup.log`.
- Local machine only. A viewer never cleans a peer.
- Recoverable by default: tracked content must be in git; scratch dirs go to the OS trash (macOS Trash; on Linux, the freedesktop trash `~/.local/share/Trash`). Untracked work is never at risk. Ignored files are the one exception, handled below, and are never removed without being listed.

**Candidate kinds:**

| kind | candidate when (all hold) | action | never |
|---|---|---|---|
| `worktree` | linked worktree (never the main one); no live session or process with cwd inside; `git status` clean, untracked included (ignored files don't count); HEAD is reachable from the default branch, or its branch is fully pushed to its upstream; idle ≥ `cleanup.worktree_idle` (default 7 d) by the latest of last session activity, last commit and mtime of the worktree's git index | `git worktree remove <path>`; then `git branch -d` (never `-D`) only if merged into the default branch; `git worktree prune` | remove the main worktree, a locked worktree (`git worktree lock`), a dirty one, or one with unpushed commits |
| `scratch` | a temp/scratch dir an adapter attributes to one session (e.g. a per-session tmp dir the agent created), owning session `dead` or `finished` ≥ 24 h, no process has a file open in it (lsof/`/proc/*/fd` check at action time), path inside the agent's known temp root | move to the OS trash (macOS Trash, freedesktop trash on Linux); if no trash is available, refuse | follow symlinks out of the root, or touch anything outside the attributed root |
| `history` | agent history store size by age (`~/.claude/projects`, `~/.codex/sessions`, `~/.gemini/tmp`, `agy` conversations) | **report only**, and point to the agent's own retention setting (e.g. Claude Code `cleanupPeriodDays`) | delete agent history: it is the agent's data, and other tools resume from it |
| `driga` | Driga's own DB, WAL, spool, feed and logs | automatic hard caps (existing event/feed caps, plus a log size cap); shown in `driga doctor` | — |

**Ignored files in a worktree candidate** are not in git, so they are classified at list time (`git status --ignored --porcelain`):
- **Build output** matches `cleanup.regenerable`: default `node_modules/`, `target/`, `.venv/`, `venv/`, `dist/`, `build/`, `.next/`, `__pycache__/`, `.gradle/`, `.terraform/`; the user can extend it. It is shown with sizes and leaves with the worktree.
- **Anything else ignored** (`.env`, local DBs, editor state) makes the candidate `needs_review` and lists the paths. Acting on it requires `--include-ignored` for that one candidate, and even `--all` never implies it.

v1.6 has no separate "delete ignored files" action.

**Size:**
- Computed on demand (`driga cleanup --sizes`, or when the TUI row is expanded), never in the collector's regular passes.
- The walk stays on one filesystem and does not follow symlinks.
- Each walk is capped at 30 s; a capped result shows as `≥`.

**Low disk:** when `machine.disk_free` falls below `cleanup.low_disk` (default 10 % of the volume or 10 GiB, whichever is smaller), the inbox gets a `low_disk` item that names the top candidates. The item is acked like any other.

**Surfaces:**
- Commands:
  - `driga cleanup` lists candidates grouped by kind;
  - `driga cleanup <id>` acts on one candidate;
  - `driga cleanup --kind worktree --all` acts on all candidates of a kind, skipping any that fail re-verification;
  - `--json` uses the standard envelope.
- TUI: a Cleanup tab.
- MCP: `list_cleanup_candidates`, read-only. MCP never deletes.

**Storage:**
- `driga cleanup` inspects live, read-only, in the CLI, as `kill.VerifyIdle` does:
  - stored `worktrees` and `sessions` rows give the list of worktrees and the last activity;
  - per worktree, `git worktree list --porcelain` gives the lock state, `git status --porcelain --ignored` the dirty state, `git rev-parse @{u}` plus `git merge-base --is-ancestor` reachability, and `git rev-parse --git-path index` the index mtime;
  - cwd for all of the user's processes comes from one `platform.Cwds` call, which lists every process, not just agent-classified ones.

  So the collector schema, the collector's passes and the feed are unchanged.
- Remote candidates are not shown in v1.6; cleanup is local-only. A future version may publish them through the feed.
- The CLI performs the action itself, as `orphans kill` does. Its log line goes to `cleanup.log`, not the DB.

## 5. Left to the builder

Exact Gemini and `agy` signature strings; which per-session scratch dirs each adapter can attribute (only ones it can prove from the agent's own records); legacy JSON size threshold; summary prompt wording; TUI key placement; `summary` feed payload fields; how `DRIGA_INTERNAL` is threaded through `hooks` and the adapters.

## 6. Decisions (2026-10-18, delegated: "You judge")

1. Summaries are **off by default**; `[summaries] enabled = true` opts in.
2. Summaries run **on demand only** (`driga summarize`, TUI `S`); there is no background LLM call.
3. `agy` schema: the maintainer runs `driga dev agy-schema` (Claude's own access was blocked by policy).
4. v1.5's `share_text = "titles"` default stands: pairing is explicit, per viewer and revocable.
5. Cleanup covers disk as well as memory and CPU, and agent histories are report_only (maintainer request, then accepted).
